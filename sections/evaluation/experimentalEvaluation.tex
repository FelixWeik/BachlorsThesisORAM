\label{sec:experimentalEvaluation}
The author implemented \textit{gmp\_mpz\_class} (\ref{sub:approachGMP}) for 64, 128, and 256 bits.
512 bits and above are also possible in theory yet exceed the storage limitations of the author's machine.
Testing larger bit-sizes is therefore left for future research given a more performant machine.

\textit{new\_input\_type} (\ref{sub:PossibilityLargerRegisterType}) has similar properties for bit-sizes.
It, too, is tested for 64, 128, and 256 bits.

The base implementation by Vadapalli et al. (\ref{sec:ExistingImplementation}) is defined for 64 bits only.
Yet, it will partake in the benchmarks for 64 bits serving as a reference.
It is called \textit{base} in the following.

\subsection{Construction}\label{sub:expEvaConstruction}
The author uses \textit{Docker} and \textit{Docker Compose} to create a uniform testing environment.
Each test runs three containers with each container resembling a single party $P_b$.
These containers are then strapped together via \textit{Docker Compose} providing networking and a uniform interface for setting testing parameters.

\paragraph{Communication and Linux Traffic Control}\label{sub:dockerCommunication}
All approaches use \textit{Boost.Asio v1.18.1} for asynchronous communication.
As each party now has its own container, messages need to be exchanged over a network.
For this purpose, a docker network using the bridge driver is used.
It allows referencing other containers by specifying their name.
As the executable requires the addresses of the other parties as input, one now simply inserts the other containers' names to reference the other parties.
The container of party $P_0$ is called \code{p0}, $P_1$'s container \code{p1}, and $P_2$'s container \code{p2}.

Using docker compose networks yields the great advantage of network manipulation via \textit{Linux Traffic Control (tc)}.
tc sets fundamental network properties such as bandwidth, latency, jitter, and burst-size.
Specifying these properties in the \code{docker-compose.yaml} or in an \code{.env} file respectively simulates different network conditions.
For testing purposes, the author chose to manipulate the bandwidth of the network and the latency of each party.
If not explicitly specified latency is set to 1ms, bandwidth to 100mbits.

\paragraph{Resulting Construction}\label{par:dockerConstruction}
These changes result in a single Dockerfile that can be reused for all implemented approaches.
It will generate a fitting Docker-Image given the source code and generate the \code{prac} executable.
Each image is tagged with the name of the approach.
This image is then referenced in the \code{docker-compose.yaml} which is unique for each approach as different images are referenced.
The compose-file itself uses an \code{.env} file to set its environment variables, such as the depth of the RDPF-Triples or the number of elements to retrieve from the database.
Each compose-file will then run the tests of the chosen approach returning the given performance numbers.
The following section describes these numbers in greater detail.

\subsection{Test Metrics and Types}\label{sub:testMetricsAndTypes}
This section describes the tests executed and the measured performance metrics.
Each party logs its own test results.
These logs show slight variations between the parties.
However, these differences are very small and occur by definition of the protocol.
Therefore, all evaluated results are based on the logs of $P_0$, or container \code{p0} respectively.
These results can be further separated into preprocessing and online phase.
Different tests and benchmarks are executed for preprocessing and writing.

\paragraph{Logs and Operations}\label{par:expOutputs}
Logs in general show the following information:
\begin{itemize}
    \item The number of messages sent 
    \item The number of message bytes sent 
    \item The number of latencies which is equivalent to the Lamport clock of each party
    \item Number of local AES operations
    \item Summarized wall clock time for both the user and the system
    \item Occupied memory
\end{itemize}
The preprocessing output additionally shows the number and depth of generated RDPF-Triples.
\code{r10:50}, for example, means 50 RDPF-Triples of depth 10.
An exemplary preprocessing log of party $P_0$ is shown in \ref{lst:examplePreprocOutput}.

Online testing results additionally print the type of operation.
In general, reads and writes can be further categorized into \textit{dependent} and \textit{independent} operations.
Executing several dependent operations can only be done in sequence, as each operation requires the information from the previous read or write.
Dependent reads, for example, require the result from the previous read to receive the index for the upcoming read.
Independent operations, however, can be executed in parallel.
All required information is known in advance.
The last type of operation, \textit{Interleaved Operations}, is a combination of executing a read followed by an update operation.
Note that this results in executing two reads in sequence before writing, as updating consists out of both reading and writing (\ref{par:DuoramWriting}). 
An exemplary online output of party $P_0$ is shown in \ref{lst:exampleOnlineOutput}.

Note that when testing for depth, values start at 3.
That is due to the fact, that RDPF-Triples of depth 2 consist solely out of three nodes - The root and its two leafs.
That allows the user to work on a database holding 4 entries.
As this is of no greater practical use, depth values start at 3.

\paragraph{Preprocessing Benchmarks and Default Values}\label{par:preprocBenchmarksNumbers}
Benchmarks in the preprocessing phase will test for the following metrics:
\begin{itemize}
    \item Wall-Clock time for increasing depth, constant number of generated RDPF-Triples, constant latency, and constant bandwidth (\ref{fig:wallClockDepthPreproc})
    \item Wall-Clock time for constant depth, increasing number of generated RDPF-Triples, constant latency, and constant bandwidth (\ref{fig:wallClockIncNumPreproc})
    \item Storage requirements for increasing depth, a constant number of generated RDPF-Triples, constant bandwidth, and constant latency (\ref{fig:storageReqDepthPreproc})
    \item Number of local AES operations (\ref{fig:aesOpsDepthPreproc})
    \item Wall-Clock time for increasing latency, constant number of generated RDPF-Triples, constant depth, and constant bandwidth (\ref{fig:wallClockIncLatencyPreproc})
    \item Wall-Clock time for increasing bandwidth, constant number of generated RDPF-Triples, constant depth, and constant latency (\ref{fig:wallClockDecreasingBandwidthPreproc})
    \item Number of sent messages for increasing depth and constant number of generated RDPF-Triples (\ref{fig:numSentMessagesIncDepthPreproc})
\end{itemize}

Testing for these benchmarks explains the runtime differences between the approaches during preprocessing.
\textit{Constant} value means the standard values are used.
The standard values for bandwidth (100mbits) and latency (1ms) as defined above remain valid.
If not specified explicitly, \textit{gmp\_mpz\_class} and \textit{base} generate 50 RDPF-Triples each.
Recall the behavior of \textit{new\_input\_type} in the online phase of aggregating multiple database entries into a single entry (\ref{sub:PossibilityLargerRegisterType}).
This means, for our bit testing range, up to four times the amount of RDPF-Triples are required.
Therefore, the standard value of generated RDPF-Triples for \textit{new\_input\_type} is 200.
The standard value for depth is 15 resulting in a database holding up to $2^{15}$ entries.

\paragraph{Online Benchmarks and Default Values}\label{par:onlineBenchmarksNumbers}
Online benchmarks will check the following metrics:
\begin{itemize}
    \item Wall-Clock time for increasing latency, constant number of elements retrieved or updated, and constant bandwidth
    \item Wall-Clock time for increasing bandwidth, constant number of elements retrieved or updated, and constant latency 
    \item Number of sent messages for increasing number of retrieved or updated items, constant bandwidth, and constant latency 
    \item Amount of message bytes sent for increasing number of retrieved or updated items, constant bandwidth, and constant latency
\end{itemize}

All the benchmarks are executed separately for reading and updating.
Executing these tests requires the preprocessing to be executed in advance.
This means 50 RDPF-Triples of depth 15 for both \textit{gmp\_mpz\_class} and \textit{base}, 200 RDPF-Triples of depth 15 for \code{new\_input\_type}.
It will, however, not be included in the online results as the preprocessing phase in benchmarked separately.

The standard values of bandwidth (100mbits) and latency (1ms) from above remain valid.
If not given explicitly, the number of retrieved or updated items per operation is set to 5.
Next, the size of the used database in these benchmarks is set to $2^{15}$.
Thus, RDPF-Triples of depth 15 are used.

\subsection{Benchmarks}\label{sub:expEvalBenchmarks}
The tests are executed on a Surface Laptop Studio with 16 GB of RAM and an Intel i5 9th generation running Ubuntu 24.04.1 LTS.
Recall each party being executed in its own container.
These containers, too, run the latest Ubuntu release.
The results are collected and plotted using seaborn.

\subsubsection*{Preprocessing}\label{subsub:expPreprocBenchmarks}
\begin{figure}
    \centering 
    \includegraphics[width=\textwidth]{plots/plots/preproc/wall_clock_preproc.png}
    \caption{Wall-Clock time for increasing depth and constant number of generated RDPF-Triples}
    \label{fig:wallClockDepthPreproc}
\end{figure}

\ref{fig:wallClockDepthPreproc} shows the general runtime for party $P_0$.
Since all parties start and end the execution at the same time, runtimes between the parties are nearly the same.
One notes big differences in runtime beginning at depth 15.
Especially the \textit{gmp\_mpz\_approaches} suffer large performance degradation beyond depth 15.
\textit{new\_input\_type}, too, deteriorates from depth 15.
Yet, it still is about $5.2x$ to $6.3x$ faster than \textit{gmp\_mpz\_class}.
Differences in performance before depth 15 are larger when seen in relation, yet it is an impractical difference and thus negligible.

Differences in runtime are also present for constant depth and varying number of generated triples.
\ref{fig:wallClockIncNumPreproc} compares all approaches and plots their wall-clock time.
One notes an almost linear behavior of \textit{gmp\_mpz\_class}, especially for 64 bit.
\textit{base} and \textit{new\_input\_type} have an almost constant wall-clock time starting at $0.04$ seconds at one RDPF-Triple up to $0.23$ seconds for $100$ RDPF-triples. 
This is about $400x$ faster than \textit{gmp\_mpz\_class} for 256 bits and $290x$ faster than \textit{gmp\_mpz\_class} for the same bit size.

Each party stores its generated RDPF-triples in a local file (\ref{par:preliminariesRDPFs}).
Its storage requirements for 50 RDPF-triples of increasing depth are shown in \ref{fig:storageReqDepthPreproc}.
\textit{base} and \textit{gmp\_mpz\_class} for 64 bit have almost similar storage requirements for depths smaller 15.
\textit{mpz\_class} is structured in \textit{limbs}.
Each limb holds 8 bytes.
When values exceed a single limb, more limbs are allocated.
\code{mpz\_class} allocates these limbs at runtime, keeping track of its capacity and current length.
Therefore, even for the same bit size, a single \textit{mpz\_class} requires about $1.5x$ more storage than \code{uint64\_t} as used in \textit{base}.
\textit{gmp\_mpz\_class}, consequently, requires more storage than \textit{base}.
Recall that \textit{new\_input\_type} requires up to four times more RDPF-triples than \textit{base} during the online phase.
Therefore, around four times the storage is required.
Note that due to the exponential growth of the RDPF-trees, storage requirements increase heavily, again starting from depth 15.

This exponential growth can also be observed in \ref{fig:aesOpsDepthPreproc}.
The graph shows the amount of local AES operations for increasing depth.
As each tree is generated by using AES as length doubling PRG (\ref{sub:BGIDPFConstruction}), one needs at least $2^n$ local AES operations to construct a tree of depth $n$.
One observes \textit{new\_input\_type} executing four times more local AES operations than \textit{base}.
This is due to \textit{new\_input\_type} generating four times the RDPF-triples of \textit{base}.
Also, the \textit{gmp\_mpz\_class} for 64 bit executes less local AES operations than its larger fellows.
There is a difference of around 2 million local AES operations between 64 and 256 bit for depth 20.
This, however, has little to no impact on the general runtime as local AES operations on \code{\_\_m128i} vectors have nearly no overhead.

The reason for the runtime differences is found when taking a closer look at the performance when varying the bandwidth (\ref{fig:wallClockDecreasingBandwidthPreproc}).
When varying the bandwidth \textit{new\_input\_type} shows the biggest drop in performance.
As seen in \ref{fig:storageReqDepthPreproc}, \textit{new\_input\_type} has the largest storage requirements.
Thus, messages become larger slowing down the communication when the bandwidth drops.
A similar effect is observed for \textit{gmp\_mpz\_class}, yet, due to smaller storage requirements and thus smaller messages, not as large as for \textit{new\_input\_type}.

Varying the latency, however, slows down \textit{gmp\_mpz\_class} but not \textit{new\_input\_type}.
Taking a closer look at the implementation explains this issue:
In \textit{base} and \textit{new\_input\_type} message are stored in a buffer.
As each message has a fixed size of 8 bites, one can store messages in a buffer of fixed size.
Once the buffer is filled, one sends it and empties the buffer.
The set buffer size directly impacts the number of sent messages.
\textit{gmp\_mpz\_class} has no such buffer as messages are of variable size.
Therefore, messages are sent directly.
Also, \textit{gmp\_mpz\_class} sends two messages where \textit{base} and \textit{new\_input\_type} require only a single message as both the size of the data and the data itself are sent separately.
This not only results in increased message overhead as shown in \ref{fig:numSentMessagesIncDepthPreproc} but also in a higher performance degradation as latency increases.
Recall that \textit{mpz\_class} values need to be serialized before sending and deserialized when received (\ref{subsub:gmpCommunication}).
This significantly slows down each communication operation.
When tested, each sending operation including serialization required $0.01$ seconds on average, receiving took $0.02$ seconds on average.
This heavily impacts performance compared with $0.0001$ seconds for sending and $0.0025$ seconds for receiving a \code{uint64\_t} message.

Finally, bit operations on \code{mpz\_class} values are less performant than on \code{uint64\_t} values.
Testing showed that especially on \code{mpz\_class} values containing multiple limbs, bit shifts and XOR operations are around $5$ times slower than similar operations on \code{uint64\_t}.
The code used for proving the performance difference is given in \ref{lst:xorMpzVs64t}.

To conclude, \textit{gmp\_mpz\_class} is less performant for all bit sizes, depths, and number of generated RDPF-triples when compared to \textit{base} and \textit{new\_input\_type}.
It executes more local bit operations, sending operations, and receive operations.
All of which are slower than its \code{uint64\_t} equivalent.
This effect becomes particularly noticeable for depths greater than 15.
For smaller depths, however, \textit{gmp\_mpz\_class} is equally performant and storage efficient.
Its performance is also better than \textit{new\_input\_type} when bandwidth is small.
This, however, is reversed when latency fluctuates while bandwidth remains constant.
Therefore, preprocessing in \textit{gmp\_mpz\_class} can be preferred for larger bit sizes when depth and latency is small compared to \textit{new\_input\_type}.
