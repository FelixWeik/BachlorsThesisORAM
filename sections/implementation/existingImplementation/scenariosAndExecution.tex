As specified in \ref{subsub:implementationMpcioAndCommunication}, \code{prac} is executed three times simultaneously.
Hence, assuming one executes locally without using docker, one needs to run \code{prac} in three terminals at once.
Executions need to be started separately for preprocessing and the online phase.
Calling \code{prac} requires several arguments: player number, which mode to execute (-p, -o, or blank), and number of threads for faster execution (-t).
For preprocessing, $P_2$ additionally requires the type, amount and depth of functions to calculate.
In the online phase, all parties require the depth of the RDPF-Triples and the amount of items to retrieve or store as input.
\code{r} represents RDPFs.

Thus, the function calls for preprocessing will look as follows:
\begin{enumerate}
    \item \code{./prac -t 3 -p 0}
    \item \code{./prac -t 3 -p 1 localhost}
    \item \code{./prac -t 3 -p 2 localhost localhost r20:20}
\end{enumerate}
Will execute preprocessing generating 20 RDPF-triples, each of depth 20.
Each instance is assigned three threads.

\begin{enumerate}
    \item \code{./prac -t 3 0 duoram 20 5}
    \item \code{./prac -t 3 1 localhost duoram 20 5}
    \item \code{./prac -t 3 2 localhost localhost duoram 20 5}
\end{enumerate}
Executes the online phase, again with three threads each.
Each read or write operation retrieves or stores 5 elements.

Execution via docker is introduced in \ref{sub:expEvaConstruction}.

\subsubsection*{General Execution}
The following sections denote the computational peers $P_0,P_1$ as "player", $P_2$ is called "server".
All executions start in \code{prac.cpp} which accommodates the \code{main} method.
This includes the starting points for both the players' and the server's computations.
It parses the given arguments, sets the addresses of the other parties, and decides whether the current execution is a player's or server's computation.
That means it calls \code{comp\_player\_main} or \code{server\_player\_main}.

\code{comp\_player\_main} represents the players' computation.
It is separated into \code{preprocessing\_comp} and \code{online\_main} representing the preprocessing computation and the computations necessary for performing the online phase.

\code{server\_player\_main} represents the server's computations.
It, too, is separated into its phases \code{preprocessing\_server} and \code{online\_main}.

The careful reader notices both the server and the player calling \code{comp\_main} albeit the previous text assumed these computations to be implemented separately.
Notice that this too is only a starting point for more specialized calculations.
Thus, \code{online\_main} further specifies its computations given the number assigned to the party.

\subsubsection*{Preprocessing} \label{subsub:implementationPreprocessing}
This phase generates messages and its contents as defined in \ref{subsub:implementationMpcioAndCommunication}.

\code{preproc.cpp} handles these computations for both the server and the players.
Given the current type, which equals the address inside the current message, the code calls the specific constructor.
Each type is assigned a certain file \code{<type><amount>.<party>.t<n>}.
For example generating 20 RDPFs will result in three files \code{rdpf20.<party\_name>.t<n>} which are used in the next phase.
Number $n$ assigned to t increments for each execution.
This means t starts at 0 and increases after every execution thus avoiding naming conflicts.

\subsubsection*{Reading, Writing, and Cyclic Shifts} \label{subsub:implementationCyclicShifting}
\code{duoram.tcc} accomodates both oblivious read and write operations.
Each operations implements its own type of cyclic shifting since it performs these shift on different types of vectors (\ref{sub:CyclicShiftingProtocol}).
Also, reading requires only two RDPFs while writing requires all three (\ref{sub:DuoramReadingAndWriting}).
The general process from \ref{sub:DuoramReadingAndWriting}, however, stays the same.

\paragraph{Cyclic Shifting for Reading}
Reading requires the player to calculate the distance of the random target index to the share of the new target.
This distance is called offset.
Each player then sends her offset to the other player and simultaneously receives the offset of the other player.
\code{ParallelEval()} then evaluates the DPFs on the new share, uses it to read from the given shape, and returns the result of the read operation.
The server receives both offsets.
It will then send the cancellation terms to the players as defined in \ref{sub:DuoramReadingAndWriting}.

Reading in general indexes into the shape implemented by the duoram.
The operation returns either \code{MemRefInd} meaning independent memory references, or \code{MemRefExpl}, which represents an explicit memory reference.
Overloads of the indexing operator are implemented accordingly.
Each reference type implements two operators that allow them to be implicitly casted into either an additively or XOR shared register entry.
This will allow the client to access the data-value of the memory reference.

\paragraph{Cyclic Shifting for Writing}
\code{Duoram::Shape::MemRefS::oram\_update()} implements the writing operation including the cyclic shift.
Both players calculate the offset, send it to the other player and receive it from the other player.
After combining the offsets, each player performs the cyclic shift, evaluates all three RDPFs and sets the database on the target index to the new target value.
The server follows the basic writing protocol which includes receiving both offsets and combining them, using the same implementations as the players.

Since writing is both reading and updating, the update operation (\code{+=}) is done on the memory reference returned by reading at index \code{ind}.
This memory-reference will then be written into the duoram automatically using the \code{duoram\_update} operation.
\code{duoram\_update} then refreshes the blinds.
