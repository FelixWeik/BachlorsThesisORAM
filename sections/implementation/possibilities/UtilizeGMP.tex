\label{sub:approachGMP}
The \textit{GNU Multi Precision Arithmetic Library (GMP)} implements integral datatypes of arbitrary precision while supporting bit operations.
This means, one can choose the amount of bits used to represent a given value or directly assert a value of arbitrary size.
It is open source and scarcely documented, yet widely used due to its efficiency and general performance.

To use GMP in a project, one needs to install \code{libgmp\_dev} first.
The author used \code{apt} for this step.
Next, make sure to add the \code{-lgmp} flag during linking as it links the project with the GMP-library.
If the project is written in C++ also include GMP's C++ wrapper \code{-lgmpxx} as it provides overloaded operators and simpler memory management.
Since the author's code compiles using a \code{MAKEFILE}, the flag is set there.
Finally, include \code{gmp.h} in the files requiring GMP.

The following sections use \code{mpz\_t} attributes frequently, which represent an integer of arbitrary size.
\code{mpz\_class} represent a class holding a single \code{mpz\_t} value providing the most common operators.
It, too, is used rather frequently in the following subsections.

\subsubsection*{Approaches}\label{subsub:gmpApproaches}
When implementing this approach, two possible solutions are considered.
\begin{enumerate}
    \item Implement a wrapper struct for a single \code{mpz\_t} value.
    This struct can then be templated to match a certain bitsize.
    Assuming this struct is called \code{value\_wrapper<BIT\_SIZE>}.
    This results in \code{DPFnode} and \code{value\_t} being called \code{DPFnode = value\_wrapper<2*VALUE\_BITS>} and \code{value\_t = value\_wrapper<VALUE\_BITS>}.
    Then, however, one needs to take care of memory management manually, overload all operators for different datatypes and still is bound to the restrictions from \ref{sec:GeneralLimitations}.
    Also, drawbacks like communication issues between parties when using these structs from the second approach still exist.
    Therefore, this approach will not be pursued further\footnote{A basic implementation of this approach, however, can be found \hyperlink{https://github.com/FelixWeik/PrivateRandomAccessComputations/tree/UnlimitedGMP}{on branch UnlimitedGMP}}.
    \item Use the built-in \code{mpz\_class}.
    It takes care of memory management, initialization, and destruction automatically.
    One, however, cannot template its predefined bitsize.
    This means sizes adjust automatically to the given value.
    These sizes adapt automatically if the value changes.
    Therefore, one can either choose if he limits the interval a number can be generated in or accept the arbitrary size of numbers.
    As this research is all about using values of arbitrary size, the author chose to go with the latter one.
    This makes this approach almost independent of macros like \code{VALUE\_BITS} (\ref{itemize:importantMacros}) as \code{\_\_m128i} vectors can be generated at runtime.
    Generating random values via \code{random\_mpz} limits the values to a certain bit size of \code{VALUE\_BITS}.
    As most of the values are chosen randomly in the beginning, no overflows given the random values are possible.
    One can simply insert any value, the program will ultimately take care of it.
    Therefore, the author chose to further pursue and implement this approach\footnote{The implementation is located \hyperlink{https://github.com/FelixWeik/PrivateRandomAccessComputations/tree/gmp_mpz_class}{at branch gmp\_mpz\_class}}.
\end{enumerate}

\subsubsection*{Basic Changes}\label{subsub:gmpBasicChanges}
To avoid cyclic dependencies, a new file \code{types.tcc} is introduced.
It declares \code{value\_t} and \code{DPFnode} as type alias for \code{mpz\_class}.
It also defines \code{VALUE\_BITS} (\ref{itemize:importantMacros}).
\code{types.hpp} then includes \code{types.tcc}.

Next, bit-utils and bit-masks need to be adjusted for the new datatype.
Bit operations like \code{XOR} and the logical \code{AND} are already defined by \code{mpz\_class}.
No changes in the calls are required.

Adjusting bit-masks, however, needs more changes.
As they are now independent of size and are not fixed to \code{VALUE\_BITS} many bits, bit-masks need to be instantiated at runtime.
It should also keep its existing syntax of indexing into a given bit-mask as this keeps the syntax consistent.
For this, a helper function \code{create\_bitmask} is created.
It takes the size and the general shape of the mask as input and creates a bit-mask of the given size.
Each invocation of different bit-masks calls the helper function with different arguments, the size is generated at runtime according to the size of the calling value.
Therefore, no syntax changes need to take place as only the base class itself changes.

\subsubsection*{Memory Management}\label{subsub:gmpMemoryManagement}
Changing \code{DPFnode} and \code{value\_t} to \code{mpz\_class} resulted primarily in \textit{Double Free} and \textit{unaligned fastbin junk} errors.
These errors are results of wrong allocations and deletions of memory locations. 

\paragraph{Double Free Error}\label{par:doubleFree}
A double free error occurs when the destructor of an object is called twice.
As it is called the second time the garbage collector tries to free an invalid memory reference ultimately resulting in a segmentation fault.
This is primarily the case when assigning an object of type \code{mpz\_class} to a temporary object.
This will not copy the \code{mpz\_class} but only the pointer.
The referenced object stays the same.
Once the temporary object is freed, freeing the \code{mpz\_class} results in a double free error.

Two primary solutions exist:
When pushing the \code{mpz\_class} object to a vector use \code{emplace\_back} rather than \code{push\_back} as it does not copy the pointer but creates a new object resulting in new pointers.
Freeing the objects separately avoids the double free error.
When assigning the \code{mpz\_class} to another temporary object use \code{std::move}.
It reassigns the \code{mpz\_class} to the temporary object, leaving the \code{mpz\_class} in an empty but valid state.
Freeing both objects separately avoids the double free error.
Keep in mind, however, that the initial \code{mpz\_class} is zero after executing \code{std::move}.

\paragraph{References and Return Values}\label{par:referencesAndReturnValues}
When passing a \code{mpz\_class} into a function, use references rather than copying the object.
Not referencing the object might not directly result in a segmentation fault, yet it will most likely crash the program due to uninitialized values.
Also, reassigning the return values to an object in the calling class will most likely result in a double free error (\ref{par:doubleFree}).
Passing objects as references will often render return values unnecessary as changes can be executed directly on the given object.
Alternatively, pass an empty \code{mpz\_class} into the function and let the function initialize the object itself.

\paragraph{Explicit and Implicit Casts}\label{par:mpzExplicitAndImplicitCasts}
Casting \code{mpz\_class} objects is not possible without using built-in functions.
This means, no implicit casts are possible.
One can, however, use built-in functions like \code{mpz\_get\_ui} to receive an unsigned integer representation without losing information.
The size of the returned value is also adapted to the size of the stored value.
Another possibility for casting values comes in especially useful when storing \code{mpz\_class} objects or using them during communication:
Serialization and deserialization.
More details on these functions are given in the following section \ref{subsub:gmpCommunication}.

\subsubsection*{Communication}\label{subsub:gmpCommunication}
Communication operations use TCP-sockets.
Each party holds two sockets which are each linked to one of the other parties.
Also, compound functions exist.
The server, for example, can utilize \code{queue\_peer()} to send the given char pointer to both peers at once.
These functions are wrapped in stream objects, which implement and overload these functions.
To send \code{mpz\_class} values, one needs to adapt the communication process.

Communication takes place not only between parties, but also within a single party while switching from preprocessing to online mode.
To reuse the RDPF-triples generated during preprocessing, each party stores its generated values in a file (\ref{par:preliminariesRDPFs}) where the stored values will be retrieved and further processed during the online phase.
On a high level both types of communication operations do not differ.
One can use almost the same functions for storing and retrieving values, but also for sending and receiving values.
The only change is the type of stream used:
Writing to files will be done using \code{std::ifstream} which stands for \textit{Input File Stream} and \code{std::ofstream} which means \textit{Output File Stream}.
Communication between peers and servers is executed by utilizing the \code{MPCSingleIOStream}, which is a wrapper for the TCP-sockets.
More on storing and retrieving these values can be found in \ref{par:overloadingStreamOperations}.

\paragraph{Size of mpz\_class Attributes}\label{par:sizeOfMPZClassAttributes}
In the basic implementation by Vadapalli et al. bit-sizes are fixed via macros.
The size of a \code{mpz\_class} value, however, is decided at runtime.
Thus, even if it generated on a given interval, bit-sizes needed to store and retrieve values vary.
This means one now needs two messages to send a single \code{mpz\_class} value: The size to allocate the required buffer-size, and the value itself.
The number of sent messages will almost double.

For this approach to work, the length of the size attribute needs to be fixed.
If it was stored as an \code{mpz\_class} one would need another size attribute to decide on its length and so on.
Therefore, the author chose to implement length attributes and the according messages solely using type \code{size\_t}.
Each length attribute will be of same length which simplifies storing and retrieving length attributes.
Note that this limits a single value to the size of $2^{64}-1$ bits, which the author figured to be enough.

\paragraph{Serialization and Deserialization}\label{par:gmpSerializationAndDeserialization}
Communication operations are implemented primarily on char pointers.
This proves true not only for communication, but also for writing and retrieving data from files.
Sending a \code{mpz\_class} without casting it first or retrieving it without casting leads to errors.
Therefore, operations for serialization and deserialization of \code{mpz\_class} values are necessary.

The author chose to implement two functions:
\begin{itemize}
    \item \code{serialize\_to\_binary} takes a \code{mpz\_class} as input and returns the value casted to a binary char pointer.
    For this, the built-in method \code{mpz\_export} is used.
    \item \code{deserialize\_from\_binary} does the opposite: It takes a char pointer and the length of the buffer as input and returns the given value in form of a \code{mpz\_class}.
\end{itemize} 

These methods are then integrated in the \code{send} and \code{receive} operations during communication, but also integrated in the \code{write} and \code{read} operations for files.

It is important, however, that these methods are only functional for attributes of type \code{mpz\_class}.
This means, when using more abstract values such as \code{RegAS} or \code{LeafNode}, one needs to disassemble the value first, send it, and finally use these pieces to reassemble it to the given value.

The communication methods for trivial datatypes such as \code{uint64\_t} are left untouched.
These datatypes can be converted implicitly.

\paragraph{Overloading Stream-Operations}\label{par:overloadingStreamOperations}
Most read and write operations are triggered by using the stream operators \code{<<} and \code{>>}.
Read and receive operations are used by first defining the stream and then the buffer of what to read.
As communication operations are asynchronous, the code will continue once a value is received.
Be careful when changing the communication sequence as this might lead to deadlocks.

These operators are then called not only on values of type \code{mpz\_class}, but also on more abstract values like \code{RDPFTriple}.
To send these more complex values one, again, needs to disassemble attributes into its single attributes and send them separately.
For this purpose, the author chose to implement \code{read\_maybe\_expanded} and \code{write\_maybe\_expanded}, which takes care of sending and receiving \code{RDPFTriples}.

Also, stream operators trigger different behavior given the type of stream.
\code{std::ifstream} and \code{std::ofstream} require read and write operations including the given file.
Serialization and deserialization needs to be executed after reading and writing as overloading operations for read and write in this standard context cannot be done.
\code{MPCSingleIOStream}, however, allows for these adjustments as it is implemented manually.
Therefore, one needs to distinguish between given streams and manipulate the sequence of called operations accordingly.
For this purpose, the author decided to template the stream operators based on the given stream:
Given streams of type \code{std::ofstream} and \code{std::ifstream}, serialization is executed before and after the read or write directly in the function.
Send and receive for stream-type \code{MPCSingleIOStream} are implemented in the communication function itself, which makes the code less repetitive.

The general shifting operator for trivial datatypes stays untouched as it is required for values of type \code{bit\_t} and \code{size\_t}.

\paragraph{Example: Sending RDPF-Triples}\label{par:exampleSendingRDPFTriples}
This paragraph demonstrates the \code{send} and \code{recv} functions of \code{MPCSingleIOStream} for RDPF-triples.

To send a single RDPF-triple, one needs to call the \code{>>} operator.
This is done by specifying the stream first and the object to send.
Sending a RDPF-triple called \code{trp} using the \code{MPCSingleIOStream} called \code{p0} is done using \code{p0 >> trp}.

A single RDPF-triple holds the target and three DPFs.
These targets are held in two forms: XOR-shared and additively shared.
This means, three calls of \code{write\_maybe\_expanded} and two additional send operations for the targets are required.

To receive an RDPF-triple, call \code{p0 << trp} with \code{trp} being assigned to an empty RDPF-triple.
It will call \code{read\_maybe\_expaded} once for each DPF and deserialize the target.
It then reassembles the given RDPF-triple.
